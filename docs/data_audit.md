# 数据完整性审计报告

> 审计时间：2026-10-22 · v2.5.0
> 工具：`scripts/audit_data_integrity.py`（可重复执行）
> 数据库：`data-raw/lottery.db`

---

## 0. 这次审计是怎么发起的

v2.5.0 修奖级规则时，顺手核对了一下 README 里的期数，发现**对不上**：
README 写"大乐透 3037 期"，而实际库内只有 **2938 期**。

差 99 期，第一反应是"采集器分页截断了"——因为缺失的模式很规律：
**每年年末最后 5~7 期都缺**，看起来像翻页上限。

于是按"大乐透每周一/三/六开奖"做了推算，得出"应有 3038 期、缺 100 期"的结论。

**但这个结论是错的。**

---

## 1. 错在哪：推算前提本身不成立

错误出在"每周一、三、六"这个假设上。
用库里的**真实开奖日期**去验证，间隔其实是 **2 天 / 3 天**交替（2 天出现 1943 次，3 天 967 次），
这对应的是另一种排期，而不是我假设的那一组星期几。

**用错误的排期去推"应有的期数"，当然会得出错误的缺失结论。**

正确的验证方式是**让数据自己说话**，而不是靠外部假设。

---

## 2. 交叉验证：官方 API 是权威

体彩官方 API `getHistoryPageListV1`（`gameNo=85`）返回：

```json
{ "value": { "total": 2938, "pages": 98, "pageSize": 30 } }
```

翻到最后一页（`pageNo=98`）返回 `07028 ~ 07001`，
即**大乐透历史上的最后一期是 070001**。

> **官方声明的总数 2938 与库存 2938 完全一致 → 库内没有缺失。**

进一步验证：

| 检查项 | 大乐透 | 双色球 |
|---|---|---|
| 库内期数 | 2,938 | 3,517 |
| 年内期号连续性 | ✅ 完全连续，无缺期 | ✅ 完全连续，无缺期 |
| 相邻期间隔（1~4天正常节奏）占比 | **99.05%** | **99.09%** |
| 跨年衔接 | ✅ 全部 ≤ 3 天 | ✅ 全部 ≤ 4 天 |
| >7 天的断层 | 20 处 | 24 处 |

**所有 >7 天的断层都能对上现实事件**：

- **春节休市**（每年 1~2 月）：9~14 天
- **2019 中秋**：9 天
- **2020 疫情停售**：大乐透 54 天、双色球 51 天

## 5. 为什么值得单独写一份审计

这次的教训很具体：

> **"缺 100 期"是一个看起来极其可信的结论 —— 它有规律、有数字、能解释成因。
> 但它建立在"每周一三五开奖"这个没验证过的假设上。**

所以审计脚本刻意采用**不依赖外部假设**的三重校验：

1. **年内期号连续性** —— 只看期号自身的序号，不涉及开奖日历
2. **相邻期间隔分布** —— 用日期算，看是否落在正常节奏
3. **跨年衔接** —— 捕捉年末/年初的边界断层

三者都通过，才敢下"完整"的结论。

同时保留了与**官方 API `total` 字段**的对拍 —— 这是唯一的外部权威。
